# v1.5.0 Release Formalization Plan

## Goal

Prepare `fafafa.ssl` for the stable `v1.5.0` release without opening new feature work. The current default batch is a release-control truth sync: keep local gates, GitHub Actions runtime evidence, versioned docs, and release contracts aligned to the same current truth, then stop before tag creation unless the user gives explicit approval.

## Architecture

This is a release-control batch, not a production-code batch.

- Use the version constants in `src/fafafa.ssl.base.pas` as the source of truth: `1.5.0` and interface version `10500`.
- Keep local release gates release-oriented and repeatable: compile gate, minimal CI gate, FreePascal TLS 1.3 completeness gate, style, and Phase 2 dry-run.
- Convert the old disabled release workflow into an active workflow that uses current gates and `RELEASE_NOTES_V1.5.0.md` instead of an inline old API template.
- Treat GitHub Actions runtime truth as part of the active release-control surface. The current truth source is manual run `25989095571` plus CI run `25989090032` on head `b95044d`, so the docs and contracts must not keep telling an older Linux-only or deferred-WinSSL story.
- Do not create `v1.5.0` until readiness is pass and the user explicitly approves.

## Task 4: Runtime Truth Sync

Default path for this plan: do not redispatch runtime workflows if the current head already has fresh green evidence. Sync the control plane to the latest successful runs instead of reopening the runtime lane without a code or workflow change that could affect it.

Current evidence to carry into docs/contracts:

- `wave-b-b2-manual.yml` run `25989095571` on head `b95044d`: `windows-gate` / `macos-gate` / `linux-gate` / `summary` all `SUCCESS`
- `CI` run `25989090032` on head `b95044d`: `SUCCESS`
- latest tag remains `v1.4.3`, so the remaining gate is approval, not runtime proof

Local guards:

- keep `test_wave_b_b2_windows_runtime_workflow_contract.sh` green
- keep `test_winssl_windows_validation_bundle_contract.sh` green
- make sure readiness, release notes, roadmap, and active workflow docs describe the green runtime evidence truthfully

Only redispatch `wave-b-b2-manual.yml` after a later change that can affect the runtime lane:

- environment failure: record tooling/runner dependency and do not open production code
- entrypoint failure: fix workflow/script path drift, then rerun the focused contract
- implementation failure: only then open a `src/fafafa.ssl.winssl.*` repair batch
